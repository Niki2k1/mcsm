MCSM has a small, versioned HTTP API under `/api/v1` for bots and scripts —
for example the [Discord bot](/integrations/discord-bot). It is separate from
the API the dashboard uses and only accepts **bearer tokens**, never login
cookies: the same personal access tokens and OAuth connections as
[AI access (MCP)](/features/ai-access), with the same scopes.

## Create a token

Open the user menu → **AI access** → *Personal access tokens* and pick:

- **Name** — so you know later what uses it.
- **Scopes** — see the table below. A bot that only whitelists players needs
  **Read** and **Whitelist**.
- **Servers** — optionally limit the token to some of your servers. Left empty,
  it covers every server you can access, including ones created later.
- **Expires** — never, or after 30 days, 90 days or a year.

The token (`mcsm_pat_…`) is shown **once**. MCSM only stores a hash of it —
delete it to revoke access.

| Scope | Role needed | In the API |
| --- | --- | --- |
| **Read** (`servers:read`) | Viewer | List servers, server status, the whitelist |
| **Whitelist** (`players:whitelist`) | Operator | Add and remove whitelisted players |
| **Operate** (`servers:operate`) | Operator | Everything *Whitelist* can (plus console and power controls over MCP) |
| **Manage** (`servers:manage`) | Manager | Not used by the API yet |

A token never has more access than you: every request checks the scope, the
token's server limit and your **current** role on that server, so revoking
your access to a server or demoting you narrows your tokens immediately.

## Authentication

Send the token as a bearer token:

```sh
curl -H "Authorization: Bearer mcsm_pat_…" https://mcsm.example.com/api/v1/servers
```

Missing, malformed, expired or deleted tokens get `401`. Servers outside the
token's limit answer `404`, exactly like servers that don't exist.

Every token may make **120 requests per minute**; responses carry
`RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` headers, and
`429` responses a `Retry-After`. Repeated requests with invalid tokens from one
address are throttled as well.

## Endpoints

Server ids are container names, e.g. `mc-survival` — the same id as in the
dashboard URL.

| Method | Path | Scope | Description |
| ------ | ---- | ----- | ----------- |
| `GET` | `/api/v1/token` | any | The calling token: kind, user, scopes and server limit. |
| `GET` | `/api/v1/servers` | Read | Servers the token can access. |
| `GET` | `/api/v1/servers/{id}` | Read | Status and online players. |
| `GET` | `/api/v1/servers/{id}/whitelist` | Read | The whitelist. |
| `POST` | `/api/v1/servers/{id}/whitelist` | Whitelist | Whitelist a player (optionally as a one-time claim). |
| `DELETE` | `/api/v1/servers/{id}/whitelist/{name}` | Whitelist | Remove a player from the whitelist. |

### Server status

```json
// GET /api/v1/servers/mc-survival
{
  "id": "mc-survival",
  "name": "Survival",
  "domain": "survival.example.com",
  "running": true,
  "ready": true,
  "players": { "online": ["Notch"], "count": 1 }
}
```

`ready` is `false` while the server is stopped or still starting.

### Whitelist

```json
// GET /api/v1/servers/mc-survival/whitelist
{ "players": [{ "name": "Notch", "uuid": "069a79f4-44e9-4726-a5be-fca90e38aaf5" }] }
```

The API uses the same player service as the [Players](/features/players) tab
and the MCP tools, working on the server's own `whitelist.json`: on a running
server changes go through RCON and apply immediately, on a stopped one the
file is edited and the change applies on the next start
(`"appliedVia": "file"`). While a server is starting, changes are refused with
`502` (RCON not answering yet) — try again once it's up.

Player names must match `^[A-Za-z0-9_]{1,16}$`.

```json
// POST /api/v1/servers/mc-survival/whitelist   {"name": "notch"}
{
  "result": "added",            // or "already-whitelisted"
  "player": { "name": "Notch", "uuid": "069a79f4-…" },
  "appliedVia": "rcon",         // or "file"
  "claim": null
}

// DELETE /api/v1/servers/mc-survival/whitelist/Notch
{ "result": "removed", "appliedVia": "rcon" }   // or "not-whitelisted"
```

Both calls are idempotent. Unknown accounts answer `404` with
`data.reason: "player-not-found"`.

### One-time claims

For self-service (e.g. "accept the rules to get whitelisted"), send a
`claimKey` — any stable, opaque id of the person asking, up to 128 printable
characters without spaces. The Discord bot uses `discord:<user id>`.

```json
// POST /api/v1/servers/mc-survival/whitelist
{ "name": "Notch", "claimKey": "discord:123456789012345678" }
```

Per server, each claim key can whitelist **one** player and each player can be
claimed by **one** key. Repeats answer `409` with a reason:

| `data.reason` | Meaning |
| ------------- | ------- |
| `key-already-claimed` | This key already claimed a player (`data.player`). |
| `player-already-claimed` | Another key already claimed this player. |

Claims are listed on the server's **Players** tab (operators and up) with the
claim key, player, time and token. Removing a player from the whitelist keeps
their claim, so nobody can claim a second account after being removed — a
manager releases the claim explicitly to allow a new one.

## Errors

Errors are JSON with `statusCode`, `statusMessage` and, where useful, a
machine-readable `data.reason`:

```json
{ "statusCode": 409, "statusMessage": "Notch was already claimed by someone else",
  "data": { "reason": "player-already-claimed", "player": "Notch" } }
```

| Status | Meaning |
| ------ | ------- |
| `400` | Invalid input (e.g. player name). |
| `401` | Missing, invalid, expired or deleted token. |
| `403` | The token lacks the scope, or you lack the role on this server. |
| `404` | Unknown (or out-of-limit) server, or unknown player. |
| `409` | Claim conflict. |
| `429` | Rate limit hit; see `Retry-After`. |
| `502` | The server didn't accept the RCON command (usually still starting). |
